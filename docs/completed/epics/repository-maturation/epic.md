## Product statement

Make the working full-x86 Batocera/Wolf project maintainable for humans and automated coding agents. Establish truthful repository guidance, applicable enforced standards and secret prevention, a maintained source layout, and reproducible real Wolf integration evidence explained in a testing README.

## Problem

Working code is a flat experiment-shaped script collection with incomplete typing/docstrings and several execution environments. Copied template docs claim tooling and verification that are not installed here. Native SSH verification was effective but its temporary coordinator was removed, so successful screenshots/probe records are not a maintained end-to-end command.

## Existing implementation

At the planning baseline, build, exact-layer packaging, stock preservation, runtime/input transport, publication and owned registration lived under experiments/gow-full-x86. That history explains the original cutover risks. The delivered installed implementation and its host, builder, remote-stdlib and stock-runtime boundaries are recorded in [modernization completion](../../../completed/specs/repository-modernization/spec.md).

Completed transport records and the [original full-x86 workspace](../../../completed/specs/gow-full-x86/spec.md) are under `docs/completed/`; [current application state](../../../current/app.md) is under `docs/current/` after guidance ticket 02's consolidation. The [tooling topic](../../../current/tooling.md) distinguishes actual configuration from attributed template evidence and unresolved compliance. See the linked research for the historical baseline and known failed alternatives.

## Hard constraints

- Preserve unchanged Batocera/Wolf/GoW sources, stock input/context behavior, complete upstream payload/metadata and additive runtime ownership protections.
- Retain the user's working deployment, protected original checkout/state, content libraries and unrelated services during planning.
- No universal overlay, per-emulator rewrites or host-installed runtime helper.
- Keep secrets out of source, logs and evidence. No permission to scan or publish private configuration is implied.
- Planning is not permission to install hooks/tools, run SSH tests, move source, format code, deploy, restart services, commit or publish.
- Historical native screenshots and tests are evidence with scope limits, not universal emulator/client acceptance.

## Non-goals

Do not import a React application or frontend-only checks just to imitate ProjectTemplate. Do not replace exact-layer Docker loading with the known metadata-losing ADD path. Do not replace actual emulator/native-input verification with an X11 receiver-only substitute. No generic deployment framework or production-wide cleanup is requested.

## Risks

Native tests can mutate userdata and contend for shared kernel input resources even when ROM mounts are read-only. Existing device-number reuse exposure is not solved by formalizing the suite. Screenshots and logs can reveal private information. Source changes can break embedded remote execution, builder bindings, fingerprint coverage or stock runtime compatibility. Broad tooling changes can mask those failures through exclusions or incorrect source measurement.
