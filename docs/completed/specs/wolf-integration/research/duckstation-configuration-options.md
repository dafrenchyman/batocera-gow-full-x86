# DuckStation configuration options for OpenGL startup

Research date: 2026-10-31. Source inspection only. No emulator, remote command, configuration edit, build, test, restart or runtime comparison was performed for this note. Existing observations remain in [DuckStation startup failure](duckstation-startup-failure.md). This note neither resolves that failure nor changes ticket or spec acceptance.

This rechecks and extends the existing note's configuration and renderer-source findings. GLES preference, the explicit X11 EGL route, ignored OpenGL adapter selection, post-context debug callbacks and preserved logging are not new discoveries.

Linux native defaults are `LogLevel=Info` and `LogToConsole=true`. [Logging defaults][logging-defaults]

## Source boundary

The official [coding rules](https://wiki.batocera.org/coding_rules#how_emulator_configuration_applies) distinguish generator-managed values from user-editable static settings. That distinction is useful here. However, the wiki's current links and examples are not the installed implementation. The exact Batocera pin is `155c2d8d304cbb53db52e9479dcf683392821d5c`; its [recipe][recipe] selects DuckStation `v0.1-7294` from `duckstation/old-releases`, resolved to `3a08ad18406efc1ddc4927a59bea715961bb63fa` in the existing provenance note. All native source citations below use that commit, with Batocera patches considered separately.

At this Batocera pin, DuckStation's ES declarations are in package-local [duckstation.emulator.yml][features] and [gfxbackend.duckstation.emulator.yml][backend-feature], not a DuckStation block in the shared `es_features.yml`. The [common recipe][common-recipe] registers the first unconditionally and the graphics API declaration only with `BR2_PACKAGE_BATOCERA_VULKAN`. The [core declaration][core-feature] applies to `psx`. Current wiki pages can retain older option names; the pinned declaration plus actual generator consumer wins. In particular, use `duckstation_gfxbackend`, not an unverified historical `gfxbackend` example. [Generator][generator]

## What the normal launcher rewrites

The [generator][generator] opens the existing case-sensitive INI, changes named settings, then writes the parser back. The path is `/userdata/system/configs/duckstation/settings.ini`, derived from `CONFIGS` in [batoceraPaths.py][paths]. The returned command sets `XDG_CONFIG_HOME=/userdata/system/configs`, and native [SetDataDirectory][data-directory] selects `$XDG_CONFIG_HOME/duckstation`. Native [InitializeConfig][initialize-config] appends `settings.ini` when no `-settings` argument was supplied. The normal Qt argv is `duckstation-qt -batch -nogui -- <rom>`, without `-settings`. [Generator][generator]

An unmanaged key survives this generator by value, not necessarily with original formatting or comments. It must still have a native consumer. Unknown INI keys surviving a parser round trip do not become supported settings. Direct edits to managed keys, including `GPU.Renderer`, `Display.VSync`, `GPU.ResolutionScale`, PGXP controls and `Main.StartFullscreen`, are replaced at the next normal generation. ES changes write Batocera options which the next generation translates into those INI keys. [Generator][generator] [Coding rules](https://wiki.batocera.org/coding_rules#how_emulator_configuration_applies)

The generator also forces `Main.SettingsVersion=3`, `StartFullscreen=true`, `StartPaused=false`, `PauseOnFocusLoss=false`, `PauseOnMenu=true`, `ApplyGameSettings=true`, `SetupWizardIncomplete=false`, and `UI.UnofficialBuildWarningConfirmed=true`. `SettingsVersion` matters: native initialization resets defaults when loading fails or the version differs. Do not overwrite the entire file with a short diagnostic fragment. [Generator][generator] [Native initialization][initialize-config]

The native-consumer caveat is real, not just a wiki concern. At the DuckStation pin, [Settings::Load][display-settings] reads `Display.Scaling`, `OptimalFramePacing` and `StretchVertically`, not the generator's `IntegerScaling`, `LinearFiltering`, `DisplayAllFrames` and `Stretch`. [Qt migration][migration] converts `DisplayAllFrames` only when an existing `Display.SyncMode` key triggers that migration, then removes both legacy keys. Therefore the corresponding ES rows prove declared/written controls, not reliable effects in this native version. Do not recommend those controls as EGL diagnostics.

This is a graphics/startup inventory, not a claim that controller, achievements or generic shared options are absent. Generic `videomode`, bezel and HUD declarations exist in [the same feature file][features]; their launcher effects are separate from a DuckStation-native EGL selector.

## Platform, API and context selection

The strongest early-stage control found is not an INI key. [ShouldPreferESContext][context] reads the process environment variable `PREFER_GLES_CONTEXT` and recognizes only the literal value `1`. It moves ES 3.2, 3.1, 3.0 attempts before desktop Core 4.6 through 3.0. It does not force GLES, limit the maximum GL version, select an adapter or switch to GLX. The ordinary order already tries all fourteen versions if creation fails. This makes it a bounded context/API-order diagnostic, not a convincing fix when a prior launch failed all desktop and ES window surfaces. It also cannot fix a failure obtaining an EGL display, which occurs before version iteration. [Context dispatcher][context] [EGL initialization][egl-init]

There is no `GPU.PreferGLES` consumer in this settings path. The proof is the actual context factory: it accepts `WindowInfo` and `Error`, chooses the platform implementation from the window type and gets the API order from `getenv`, not settings. Adding `PreferGLES` to the INI or inventing `.duckstation.*` pass-through does not reach it. The complete [generator][generator] has explicit named settings mappings, no arbitrary native-key forwarding and no custom-config-file option. Whether an inherited environment variable can reach the final process is a launcher/environment question, not a new `batocera.conf` key.

Qt's platform is earlier still. [Qt main][qt-main] constructs `QApplication` before DuckStation loads its INI. [QtUtils][window-info] turns Qt `xcb` into X11 window/display handles, and `wayland` into Wayland handles. The [generator][generator] explicitly sets `QT_QPA_PLATFORM=wayland` when `WAYLAND_DISPLAY` is nonempty, otherwise `xcb`. Native INI keys cannot switch an already-created Qt platform. The coordinator's runtime-adapter audit owns which display environment Wolf supplies; this note does not propose a Wayland switch or assume a compositor endpoint exists.

For X11, [OpenGLContext::Create][context] calls `OpenGLContextEGLX11::Create` directly. There is no runtime GLX alternative in that dispatcher. The [EGL-X11 implementation][egl-x11] tries explicit `EGL_PLATFORM_X11_KHR` acquisition gated on the `EGL_EXT_platform_x11` extension, then legacy `eglGetDisplay`. It tries the EXT window-surface function before legacy `eglCreateWindowSurface`. No settings parameter chooses these branches. `QT_XCB_GL_INTEGRATION` cannot turn this explicit DuckStation EGL call into GLX. External EGL/driver environment selectors may affect the implementation it loads, but they are not native DuckStation INI settings or a license to change host boot drivers.

[EGL CreateContext][egl-create] chooses an API-compatible window config from fixed RGB/alpha sizes based on `WindowInfo.surface_format`, requests context major/minor versions, binds OpenGL or ES, then creates a surface and makes it current. It receives no resolution-scale, MSAA, VSync, texture, PGXP or debug-device argument. The [Qt window-info function][window-info] does not expose an INI-controlled surface-format override. In this path, reducing enhancements cannot alter EGL display acquisition or the selected window-config attributes.

## Why common graphics toggles are too late

The order is explicit: [GPUDevice::Create][device-create] acquires a native render window, calls the API-specific `CreateDevice`, then opens shader caches and creates base resources. [OpenGLDevice::CreateDevice][gl-device] creates the GL context first, checks API availability, then applies the swap interval, debug callbacks, feature checks and buffers. [System::CreateGPU][create-gpu] creates the host device before constructing the emulated hardware/software GPU.

Consequently, `VSync=false`, native resolution, no antialiasing and PGXP off can simplify later rendering diagnostics, but they do not address a failure inside `eglGetDisplay`, `eglChooseConfig` or `eglCreateWindowSurface`. VSync is already false and resolution scale already 1 by generator default. `GPU.UseDebugDevice=true` and feature-disable flags are also too late for the documented EGL failure boundaries. Vulkan success remains a useful renderer comparison, not OpenGL acceptance. `Software` is not even a guaranteed EGL-free diagnostic: [GetRenderAPIForRenderer][renderer-api] sends Software to `GPUDevice::GetPreferredAPI`, which can still select a graphics device for presentation.

## Relevant Batocera patch effects

Read against the [complete pinned package tree][package-tree], not an unpatched upstream binary assumption:

- [001-path-program.patch][patch-program] fixes AppRoot and resources under `/usr/share/duckstation`; [003-path-language.patch][patch-language] relocates translation lookup. The settings/DataRoot path remains the XDG path described above.
- [004-adjust-paths.patch][patch-folders] hardcodes native BIOS, cache, saves, shaders, textures and per-game-settings directories. A preserved `Folders.*` value is not necessarily effective. In particular, the native game-settings directory is `/userdata/system/configs/duckstation/gamesettings`, while cache is `/userdata/system/cache/duckstation`.
- [013-fix-qt6.10.patch][patch-qt] adds Qt GuiPrivate discovery and linkage. It does not introduce an INI-selectable platform or EGL/GLX switch.
- [011-fix-shaderc-compile-error.patch][patch-shaderc] changes the shader compiler call signature. Shader compilation follows device creation, so it does not add an EGL startup option.
- The remaining package patch targets concern path display names, Discord, Linux detection, SDL input, ARM/SIMD/compiler compatibility, lightguns and notification placement. None adds a native setting consumer to the context/display/config/surface functions cited above. Board-specific legacy DuckStation patches are not substituted for this package. [Pinned tree][package-tree]

## Ranked source-backed candidates and negatives

1. Use the unmanaged logging section in an isolated, separately authorized profile if another experiment is needed. `Dev`, empty filter and file logging can expose extension/platform and context-stage detail missing at `Info`. This has the best diagnostic value without pretending to repair EGL.
2. Treat `PREFER_GLES_CONTEXT=1` as the only identified DuckStation-owned early API-order diagnostic. It needs a proven final-process environment route. It is not a native INI option, does not bypass EGL display acquisition, and an all-fourteen-versions surface failure already limits its likely value.
3. Audit actual native per-game overrides and legacy-key migrations before reasoning from the base INI. A preserved base value is not proof of the effective request. Do not edit or delete game-settings files as part of this source-only research.
4. Do not spend the next EGL-display/surface experiment on upscaling, PGXP, VSync, debug-device, shader-cache or feature-disable toggles. Their consumers are later. Do not recommend `GPU.Adapter` for OpenGL, imaginary `GPU.PreferGLES`, generic `.duckstation.*` forwarding, or stale wiki keys without a pinned consumer.

No candidate above has been runtime-tested by this research. No configuration-only OpenGL repair was established. The useful result is a narrow supported diagnostic path and a clear boundary between actual early context selection and later rendering options.
