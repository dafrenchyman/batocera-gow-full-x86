### Generic media and BIOS boot-error dialogs are not a pipe protocol

[BootSystem][system-boot] adds `Failed to open CD image '<name>':` to an `Error` and returns false. [LoadBIOS][system-bios] returns false when `BIOS::GetBIOSImage` fails. An important observation is therefore unreachable through the existing reader: a boot failure reported only in that message box has no source-proven media/BIOS failure line to classify. Do not invent `E(BootSystem): Failed to boot system` or promote an unframed `No BIOS image found` string. Positive info lines such as loading a CD or using a BIOS are not failure causes. ## Implemented consumer API and retention

These contracts are implemented in [the current probe](../../../../../src/batocera_gow/runtime/emulator_probe.py). They are no longer pending RED APIs.

1. `PrivateOutput.snapshot_available() -> tuple[bytes | None, dict[str, object]]` returns a detached latest window of at most 65,536 bytes and metadata captured with it. If the window cuts its first physical line, discard that partial line rather than treating it as a fresh record. It uses the same owned drainer's currently retained bytes, without joining, waiting for EOF, another descriptor reader or a subprocess. Metadata contains `available`, `snapshot_bytes`, `truncated` and the existing `retained_bytes`, `eof`, `overflow`, `read_failed`, `cancelled`, `draining` flags. Clipping sets `truncated`, even when discarding the cut first line leaves fewer bytes. EOF false is available partial-stream evidence. Overflow, read failure or cancellation yields `None`, zero snapshot bytes and `available: false`. A closed reader never resurrects cleared bytes. Returned bytes remain ephemeral and must not enter a report or hash.
2. `duckstation_startup_failure(output: bytes | None) -> dict[str, object]` examines at most the latest 65,536-byte window without splitting an unbounded input into all its lines. Skip a cut first physical line. Select the source-exact stock stderr record, ending at the next stock logger envelope, then examine at most 256 complete payload lines within that record. Unrelated configgen prelude does not spend that payload-line budget. Return exactly `status`, `roles`, `bytes_scanned`, `lines_scanned`, `truncated`, `partial_line`. Status is `matched`, `unmatched` or `unavailable`. `None` is unavailable with zero counts and no roles. Empty available bytes are unmatched. Byte clipping or the payload-line limit sets `truncated`; a cut first line or unterminated final line sets `partial_line` and never matches. Counts describe the bounded examined window and selected complete payload lines. Output contains no captured text, paths, environment values, bytes or hashes.
3. `EmulatorProbe.observe_startup_failure()` freezes one optional `startup_failure_diagnostic` for DuckStation before any chord. Its fields are `launcher_code`, `private_output`, `log_observation`. Only observed pre-chord pinned-process death or launcher completion permits one settle through existing `PrivateOutput.read_complete(timeout=0.25)`. After that call, freeze `snapshot_available()` even if EOF was not reached. Failure/cleanup retention may trigger this same observation, but must not wait on an ordinary live startup or create a diagnostic without observed death/completion. No lifecycle `Clock.sleep`, retry, new drainer or stock forwarding change. Keep the existing completed-launcher exception diagnostic unchanged. Preserve the original lifecycle exception, failed status, no chord and absent passing transition. Diagnostics do not become an acceptance oracle.
4. `retain_boundary` includes the same frozen diagnostic in incomplete failure/cleanup snapshots and the final result. Later bytes, EOF, cancellation, repeated observation and cleanup cannot settle again or replace it. The reader still clears its private buffer during normal cleanup. Post-chord failures do not acquire this startup diagnostic. The bounded settle does not guarantee upstream forwarding, and a known failure remains nonpassing even when no role is available.

A match is an untrusted observation from application-controlled log bytes, not authenticated attribution. Even a complete exact source-shaped line can be spoofed. Snapshot truncation, line limits, partial lines, unavailable streams and unmatched output must remain visible. Successful native Guide+Start acceptance still needs all original observations; no diagnostic can make pre-chord death pass.

## Renderer-dependent startup source findings

### Qt provides the X11 window; DuckStation creates an EGL context

[QtUtils::GetWindowInfoForWidget][qt-window-info], lines312-341, maps Qt platform `xcb` to `WindowInfo::Type::X11`. It obtains the native `"display"` resource and `widget->winId()`. The Wayland branch instead takes the native `"surface"`. An unsupported platform emits `Unknown PNI platform ` through `qCritical` and returns no window information.

[OpenGLContext::Create][gl-context] dispatches an X11 window directly to `OpenGLContextEGLX11::Create`. [Its Linux build definition][gl-build], lines112-129, includes the EGL and EGL-X11 implementations. There is no GLX-versus-EGL runtime selector in this pinned X11 renderer path. Qt's XCB platform does not mean DuckStation uses GLX, and `__GLX_VENDOR_LIBRARY_NAME=nvidia` does not select the vendor for this EGL context. Changing Qt GL integration would not replace the explicit DuckStation EGL-X11 creation path.

[OpenGLContextEGLX11::GetPlatformDisplay][egl-x11] first requests `EGL_PLATFORM_X11_KHR`, gated on the literal client extension `EGL_EXT_platform_x11`. [TryGetPlatformDisplay][egl-init] queries client extensions with `eglQueryString(EGL_NO_DISPLAY, EGL_EXTENSIONS)` and obtains `eglGetPlatformDisplayEXT` through `eglGetProcAddress`. If that path supplies no display, it tries `eglGetDisplay` with Qt's native display. Window-surface creation similarly tries `eglCreatePlatformWindowSurfaceEXT`, passing a pointer to the X11 window, then falls back to `eglCreateWindowSurface`. These are alternative EGL entry points, not a fallback to GLX. A missing platform extension alone is not fatal if the fallback works.

### Context negotiation and renderer requirements are separate

[OpenGLContext::Create][gl-context] tries desktop Core versions4.6 down through3.0, then ES3.2,3.1,3.0. `PREFER_GLES_CONTEXT=1` moves the ES entries first; it neither forces GLES nor chooses another GPU or GLX. [CreateContext][egl-create] chooses an EGL window-capable config for the requested API and color format, binds `EGL_OPENGL_API` or `EGL_OPENGL_ES_API`, and requests major/minor versions. Although the desktop entries are named `Core`, this EGL implementation sets major/minor attributes without an explicit `EGL_CONTEXT_OPENGL_PROFILE_MASK`. Each successful version must also create a surface and pass `eglMakeCurrent`.

Only then does `OpenGLContext::Create` log `Created an OpenGL context` or `Created an OpenGL ES context`, load GL/GLES entry points through GLAD using `eglGetProcAddress`, and log `GL_VENDOR: {}`, `GL_RENDERER: {}`, `GL_VERSION: {}` and `GL_SHADING_LANGUAGE_VERSION: {}`. The "Created" line precedes GLAD loading, so it alone does not establish usable GL functions. The GL strings establish a later boundary, but not successful device buffers, shaders or PS1 rendering.

[OpenGLDevice::CreateDevice][gl-device], lines301-310, reports `OpenGL renderer unavailable, your driver or hardware is not recent enough. OpenGL 3.1 or OpenGL ES 3.1 is required.` Its actual predicate is desktop `GLAD_GL_VERSION_3_0 || GLAD_GL_ARB_uniform_buffer_object`, or GLES `GLAD_GL_ES_VERSION_3_1`. Keep that distinction rather than substituting the message for the implemented test. The user-facing message is sent through [Host::ReportErrorAsync][qt-report], which logs before queuing a dialog.

[CheckFeatures][gl-features] then derives optional capabilities. Missing buffer storage disables PBO uploads; insufficient texture-buffer capacity disables that route and can select SSBO emulation; missing both produces a performance warning. Dual-source blend uses GL3.3 or blend-function extensions plus a nonzero limit. Framebuffer fetch, sample shading, geometry shaders and program-binary caching have their own feature checks. This function ends by returning true. Those warnings do not themselves prove a fatal minimum-extension failure. Device buffers can still fail afterward in [OpenGLDevice::CreateBuffers][gl-buffers].

[System::CreateGPU][system-renderer] first requires [Host::CreateGPUDevice][host-device]. Failure there returns before software-renderer fallback. After a usable device exists, `GPU_HW::Initialize` compiles pipelines and creates the PS1 framebuffer. [That function][hw-initialize] logs `Failed to compile pipelines: {}` or `Failed to create framebuffer`; [OpenGLShader::Compile and CompileProgram][gl-pipeline] can log `Shader failed to compile:\n{}` or `Program failed to link:\n{}`. These are renderer/resource failures after context creation, not evidence that the EGL display could not initialize.

### Adapter and settings interpretation

[Settings::Load][gpu-settings] supports `[GPU] Renderer`, `Adapter`, `UseDebugDevice`, `DisableShaderCache` and feature-disable keys. The stock [generator][generator-graphics] explicitly writes `Renderer` from `duckstation_gfxbackend`, default `OpenGL`, and preserves keys it does not assign. `UseDebugDevice` enables the OpenGL callback only after context creation and only with `GL_KHR_debug`; it cannot expose an earlier EGL failure by itself. It also explicitly permits `libGLX_nvidia.so` as a Vulkan ICD. A mapped library with "GLX" in its filename during Vulkan therefore does not establish GLX context use.

The NVIDIA [EGL Xlib/XCB external platform source][nvidia-egl-x11] documents a driver interface supported in560-series or later drivers, plus dependencies on XCB, GBM, DRM and Xlib. Xwayland24.1 or later is required for full explicit-sync functionality, not stated as a universal basic-startup minimum. This component reference is not an observation that the target has that module, driver version or incompatibility. The DuckStation X11 path uses an Xlib display even though Qt calls its platform `xcb`; absence of a separate XCB platform module alone would not diagnose this path.
