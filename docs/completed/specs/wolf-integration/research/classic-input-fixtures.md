# Research: classic-system input fixtures

## Question

Which concrete, rights-supported fixtures can demonstrate guest input through the four required classic-system cores, particularly where the existing SNES CPU test and Atari color bars cannot? A useful answer needs source-level press, hold, release and changed-input observations, a stock cartridge launch route, and an honest account of binary availability, assets and build dependencies. It does not need a passing native run during planning.

## Context

This report supports [Wolf Integration exploration](../explore.md#fixture-and-controller-contracts) and [the fixture contract](../spec.md#existing-media-catalog-and-private-folder-selection). It extends, without changing, the [existing fixture research](../../../../completed/epics/repository-maturation/research/emulator-fixtures.md) and [candidate catalog](../../../../completed/epics/repository-maturation/research/artifacts/fixture-candidate-catalog.json). The fixed cases remain `nes/libretro/fceumm`, `snes/libretro/snes9x`, `megadrive/libretro/genesisplusgx` and `atari2600/libretro/stella`. DuckStation and original Xbox/xemu remain required elsewhere. RPCS3 and Xbox 360/Xenia remain named nonblocking expanded targets.

The conservative conclusion is to keep the NES and Genesis leads, investigate PVSnesLib's actual controller sample for SNES, and investigate 8bitworkshop's joystick-driven `controls.a` for Atari. The last two are substantially better input leads than CPU results and color bars. None is execution-qualified or approved as a fixture bundle by this report.

## Method and limits

Research used repository planning sections, the four catalog entries, first-party GitHub tree and release APIs, immutable source files, upstream license texts and Libretro core documentation. Searches varied between controller-test ROMs, SDK input examples, hardware diagnostics and Atari joystick examples. Source inspection followed the input polling into guest rendering and checked build rules rather than relying on repository descriptions.

No Git command, SSH operation, install, build, formatter, test, emulator execution, ROM/firmware/binary download or screenshot capture occurred. GitHub tree metadata about binaries was read, not the binaries themselves. There are no locally measured fixture hashes, reproducibility results, timing measurements or native assertions. Source-derived expected behavior below is marked **[INFERENCE]** where it predicts execution. Current Libretro documentation establishes a format lead, not compatibility of a particular packaged core revision. One guessed Dockerfile URL returned 404; inspection of the upstream tree located the actual platform-specific Dockerfiles. No conclusion rests on that failed fetch.

## NES/FCEUmm

### Artifact identity and rights

The source pin is `019a524b6b042c1ea1c2e8414e79f152d5997ab3`, the v0.23 revision already recorded in the catalog. The [release API](https://api.github.com/repos/pinobatch/240p-test-mini/releases/tags/v0.23) lists `240pee.nes`, asset ID `97920507`, size 65,552 bytes, and `digest: null`. Its [published download URL](https://github.com/pinobatch/240p-test-mini/releases/download/v0.23/240pee.nes) is an acquisition reference only. No download occurred. A release tag/source association does not establish that rebuilding that revision produces those exact bytes.

The [pinned NES README](https://github.com/pinobatch/240p-test-mini/blob/019a524b6b042c1ea1c2e8414e79f152d5997ab3/nes/README.md) grants GPL-2.0-or-later for the program and names contributors. The [controller implementation](https://github.com/pinobatch/240p-test-mini/blob/019a524b6b042c1ea1c2e8414e79f152d5997ab3/nes/src/padstest.s) has its own Damian Yerrick GPL-2.0-or-later notice. Distribution of a ROM requires the appropriate notices/license and corresponding source under the selected GPL route, including build scripts and embedded resource inputs. Publishing a source URL alone is not an automatic substitute for satisfying that distribution obligation.

The [asset replacement record](https://github.com/pinobatch/240p-test-mini/blob/019a524b6b042c1ea1c2e8414e79f152d5997ab3/common/docs/assets.md) specifically explains replacement of Gillian, Motoko, Hepsie, Sonic-like scrolling art, KiKi KaiKai tiles and the PLUGE shark. This is affirmative provenance evidence for this port. It does not license the original suite's artwork on other platforms. The NES ROM is a complete suite, not merely its controller screen. Its inventory includes controller images, font, patterns, portraits, backgrounds and a DMC audio input. Preserve and review the whole shipped input set rather than claiming that selecting the controller activity removes unrelated embedded assets from the artifact.

### Stable input observation and guest controls

`do_fcpads_test` loads the ordinary controller layout. `do_pads_kernel` reads the serial controller data each frame, resets the OAM write count, draws a circle for each pressed button and clears unused OAM entries. `nes_buttons_draw_obj` checks the corresponding serial bit before emitting a pressed-button circle. The release description independently describes white circles showing buttons pressed.

**[INFERENCE]** With the ordinary NES controller screen established and all buttons released, player 1 A should have no pressed circle. Holding plain A should place the circle at A, releasing A should remove it, and pressing B after release should place the circle at B instead. A qualification assertion can classify those specific indicator locations against the unchanged controller image. A no-input negative control must remain neutral throughout the same observation window. This is stronger than noticing any changed pixel, and does not require a whole-frame hash. The circle's screen coordinates after stock scaling/cropping, its classifier, thresholds and observation budget are not yet measured.

Do not apply the README's general activity controls blindly to this screen. The [controller kernel](https://github.com/pinobatch/240p-test-mini/blob/019a524b6b042c1ea1c2e8414e79f152d5997ab3/nes/src/padstest.s) handles ordinary controller screens with a Select+Start hold exit using `SERIAL_EXIT_HOLD_TIME = 30`. Plain A, B and Start can be shown as input there. The input-selection menu uses A to select, B to return and help behavior; elsewhere Start shows help, and holding Start at boot enters MDFourier. Qualification must establish the ordinary controller activity before interpreting a button, release the menu-navigation buttons, and keep Start released during boot. Select+Start returning to an in-ROM menu is not host Guide+Start exit evidence. Button-dependent generated tones are present too, but this recommendation uses the visible circles, not audio recognition.

### Build dependencies and launch route

The [pinned makefile](https://github.com/pinobatch/240p-test-mini/blob/019a524b6b042c1ea1c2e8414e79f152d5997ab3/nes/makefile) supplies the complete target-level dependency graph for `240pee.nes`. It needs GNU Make, a POSIX shell and ordinary shell utilities, cc65's `ca65` and `ld65`, Python 3 with Pillow, and a host C compiler plus C runtime/development libraries to build `common/tools/dte.c`. On non-macOS the supplied C flags request static host linking, so static C runtime availability is a real prerequisite. The graph also uses Git's `describe --tags`, `tr`, `cmp`, `cat`, `touch` and `cp` to embed a revision string into generated help. A source archive without usable tag metadata needs an explicitly documented, accepted way to supply that same value; do not call it byte-reproducible without doing so. All `nes` sources, linker configurations, image/audio inputs, local tools and referenced `common` tools/assets at the pin must be retained. ZIP/advzip and an emulator are distribution/run convenience targets, not requirements for the single ROM target. Compiler, Python/Pillow and host tools retain their own distribution terms, separate from ROM rights.

`240pee.nes` is the normal UNROM build, not an NSF or a different mapper variant. The catalog advertises `.nes` under `nes`, and [FCEUmm documentation](https://docs.libretro.com/library/fceumm/) supports `.nes`. The stock route is an ordinary NES cartridge selected through EmulationStation/emulatorlauncher with `libretro/fceumm`, not upstream's Makefile emulator command. No FDS BIOS or Game Genie asset is needed for this cartridge. Exact tool versions, release-to-source correspondence, acquired ROM SHA-256 and native behavior remain unproved.

## SNES/Snes9x

### First choice: PVSnesLib controller sample

The inspected source revision is `e090f001ccffdc0fb69f479a8c9703e30d07f6b1`, returned by the [upstream tree API](https://api.github.com/repos/alekmaul/pvsneslib/git/trees/e090f001ccffdc0fb69f479a8c9703e30d07f6b1?recursive=1). This is a pinned inspected revision, not a claim that it equals the 4.6.0 release tag.

The [actual controller program](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/snes-examples/input/controller/controller.c) initializes a text screen headed `PAD TEST` and `USE PAD TO SEE VALUE`. It repeatedly reads `padsCurrent(0)` and prints `A PRESSED`, `B PRESSED`, `START PRESSED`, directional names and the other standard SNES button names. The default case writes spaces. The [input header](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/pvsneslib/include/snes/input.h) defines `padsCurrent` as the current pad state and says the VBlank ISR reads inputs on non-lag frames.

**[INFERENCE]** A released baseline should show the heading and a blank status field. A held A should show `A PRESSED` while held, release should blank the field, and a separate B press should show `B PRESSED`. Classifying the named status field with a qualified text/template predicate can distinguish the two inputs from neutral and from each other. The source uses an exact-value `switch`, not one independent indicator per bit. Two simultaneous buttons fall into the blank default case. Therefore blank alone cannot prove release without controlling the rest of the input state. Test one button at a time, with a demonstrated neutral interval between different names. The implementation does not erase before printing a shorter new name, so a direct transition from a longer name to a shorter name could leave trailing characters. The neutral interval avoids relying on that behavior without modifying the ROM.

Start and Select only print their names in the inspected loop. There is no menu or guest exit branch. Plain Start must still be observed separately from Guide+Start. This is a simpler host-shortcut companion than a game where Start pauses or quits, but it does not itself establish any host shortcut.

The [library license file](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/pvsneslib/pvsneslib_license.txt) and the input header actually contain the three-clause zlib-style grant. Do not flatten that difference into an all-MIT bundle based on the README badge. Preserve both notices and file-specific terms.

The sample's only explicit art input is `pvsneslibfont.bmp`. Its [data assembly](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/snes-examples/input/controller/data.asm) includes the converted font data, while the [sample makefile](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/snes-examples/input/controller/Makefile) converts that BMP. The repository grant supports it as a candidate, but no independent original font-author statement was established. It is not a procedural font generated by this project. Do not silently replace it or treat other SDK sample artwork as cleared. No imported music is declared by the controller sample, but the standard build links the SDK object set, so that observation does not clear every byte of the eventual cartridge.

The [SDK rules](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/devkitsnes/snes_rules) require `PVSNESLIB_HOME`, Make and a POSIX environment, `816-tcc`, `816-opt`, `wla-65816`, `wlalink`, `gfx4snes`, SDK headers, generated `hdr.asm`, the generated font `.inc`/data assembly and the matching `pvsneslib/lib/LoROM_SlowROM` object set. The [library makefile](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/pvsneslib/Makefile) also builds SNESMOD, default-font resources and library sources. Those are dependency/rights inputs even though this sample does not request a song. A final record needs the linked-object inventory, not just `controller.c`.

For a source-built SDK, the [compiler makefile](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/compiler/Makefile) and [submodule declarations](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/.gitmodules) identify these pins:

- `alekmaul/tcc` at `cc076f049282b7f8ca46b15c437db97d9224e763`. Its [README](https://github.com/alekmaul/tcc/blob/cc076f049282b7f8ca46b15c437db97d9224e763/Readme.md) states LGPL and points to `COPYING` and `RELICENSING`. Its nested doxygen CSS submodule is a documentation input, not a cartridge dependency.
- `vhelin/wla-dx` at `6fa1f673f010e4fa4571c40929019cd7e67d1bbd`. Its [README](https://github.com/vhelin/wla-dx/blob/6fa1f673f010e4fa4571c40929019cd7e67d1bbd/README.md) specifies GPL-2.0-or-later, a C compiler and CMake, with Sphinx optional for docs. `wla-spc700` is needed for the SDK's sound-driver build.

The [upstream Debian build environment](https://github.com/alekmaul/pvsneslib/blob/e090f001ccffdc0fb69f479a8c9703e30d07f6b1/docker/debian/Dockerfile) names build-essential, GCC 12, CMake, Make, Git, Doxygen, texi2html and TeX packages. Documentation packages are not intrinsic to compiling the controller. That Dockerfile uses `debian:latest`, testing repositories and upgrades. It is not an immutable reproducibility recipe. A qualified SDK acquisition or a pinned source-build environment, with per-tool notices and any transitive host-tool requirements, is still needed. This report identifies the target inputs but does not claim a completed clean-machine SDK bootstrap audit.

The [4.6.0 release API](https://api.github.com/repos/alekmaul/pvsneslib/releases/tags/4.6.0) publishes OS-specific SDK ZIPs, not a separately named controller ROM. The Linux ZIP's API digest is `sha256:db08f2f95400125f8ae0cc62e87c3c350fa46a3eadb3174dd3161606ee49c84c`. That is upstream package metadata, not a locally verified hash or a `controller.sfc` hash. Archive contents were not downloaded or inspected. Do not assume the ZIP contains a ready controller ROM or matches the inspected source revision byte for byte.

The sample target is `controller.sfc`, with default LoROM/SlowROM rules. The catalog and [Snes9x documentation](https://docs.libretro.com/library/snes9x/) support `.sfc`. Use the normal `snes` stock launch/configgen route with `libretro/snes9x`, not a compiler-produced loose executable. This plain cartridge requires neither BS-X nor Sufami Turbo firmware.

### Second choice and rejected substitution

[Undisbeliever's joypad bounce test](https://github.com/undisbeliever/snes-test-roms/blob/ac6ef8006809c0ff5dabc8ff137a4623967697fe/src/hardware-tests/joypad_bounce_test.asm), pinned at `ac6ef8006809c0ff5dabc8ff137a4623967697fe`, is a genuine input-sensitive first-party alternative. The file has an explicit Marcus Rowe Zlib notice. It polls twelve bits on controller port 1 each scanline, records press/release history, waits for a released interval, then renders paired vertical traces and increments a displayed read counter. It explicitly warns that it is designed for one button at a time and cannot read controllers while constructing its HDMA tables. Its data inputs include generated scanline-pattern tiles and digit tiles, not just procedural colors, so resource rights remain part of qualification.

**[INFERENCE]** A completed press/release should update the associated trace pair and counter; no input should not fabricate that same event history. Unlike the PVSnesLib sample, this is not a live held/released label. The state machine and render traces need a more involved semantic assertion, and emulator handling of scanline-level polling needs actual qualification. The [tree](https://api.github.com/repos/undisbeliever/snes-test-roms/git/trees/ac6ef8006809c0ff5dabc8ff137a4623967697fe?recursive=1) pins `bass-untech` at `9db6088a378061afc7b82f50997a5b9a1d951175` and supplies a GNUmakefile and graphics resources. This is a second research lead, not a fully audited alternative toolchain or established release binary. It ranks below the simpler live controller sample.

The existing MIT `gilyon/snes-tests` CPU artifact remains useful CPU/render evidence, but it cannot satisfy guest-button acceptance. Original 240p SNES artwork and commercial controller-test cartridge download sites are not rights-cleared shortcuts around this work.

## Mega Drive/Genesis Plus GX

### Artifact, behavior and rights

The [v2.11 tree API](https://api.github.com/repos/Stephane-D/SGDK/git/trees/v2.11?recursive=1) resolves to `ef9292c03fe33a2f8af3a2589ab856a53dcef35c`. Its [joy-test output tree](https://api.github.com/repos/Stephane-D/SGDK/git/trees/7b4e5f881aaf6a6fe76dbb3d71bdff5190d2d64c) lists `rom.bin`, 131,072 bytes, Git blob ID `c118b334774e058784a973dac79961a0990bffd6`. This is a published committed ROM. That Git object ID is metadata about a blob, not a locally measured file SHA-256. The binary was not fetched, hashed or rebuilt.

The [pinned program](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/sample/joy-test/src/main.c) continuously calls `SYS_doVBlankProcess` and `showPortState`. It prints port/controller types and the letters `U D L R A B C S`, plus `X Y Z M` for a six-button pad. `printChar` chooses text palette 1 for a set input bit and palette 0 otherwise. Each frame rereads `JOY_readJoypad`; this is not a press-only counter.

**[INFERENCE]** After the first controller row identifies a pad, a plain A hold should change A's glyph palette and no other unpressed glyph. Release should restore A's neutral palette. A separate B hold should change B instead. Independent bit checks allow simultaneous held indicators too. Qualification can classify those particular glyphs and palettes against neutral and changed-button controls. Native colors, scaled positions and thresholds remain unmeasured. The code assigns color 31 to `0x0222`, so do not assume the pressed indication means a particular bright color without inspecting actual rendering.

No menu or exit button branch appears in this sample. Start is the `S` indicator and Mode is `M` for a six-button controller. Port 2 is explicitly configured for Phaser support in the checked source; use port 1 for the ordinary-pad case rather than assuming both ports have identical behavior. The six-button device profile must come from supported stock configuration and actual core discovery, not a per-emulator input patch. Three-button coverage does not prove six-button mapping.

The [SGDK license](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/license.txt) grants MIT terms. The [README](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/readme.md) separately identifies GCC/libgcc GPLv3 terms and the [GCC runtime exception](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/COPYING.RUNTIME). Preserve source/sample/library notices and record the actual compiler and runtime provenance. The exception is conditional permission for eligible compilation, not a license for every tool bundled with an SDK.

The joy-test source directory contains only the program and boot sources, with no sample-specific image/music directory. That is good, but not an asset-free ROM. [SDK resource declarations](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/res/libres.res) include `font_default.png`, `sgdk_logo.png` and `stop_xgm.bin`. The sample uses SDK text drawing. The root grant supports the font as a candidate but this investigation did not establish an independent original font-author record or prove which default resources the committed ROM actually embeds. Review library/startup linkage and the eventual link map. Do not claim that imported Sonic artwork elsewhere in SGDK is licensed by the MIT label or needed by joy-test.

### Build and stock cartridge route

The [generic makefile](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/makefile.gen) and [common variables](https://github.com/Stephane-D/SGDK/blob/ef9292c03fe33a2f8af3a2589ab856a53dcef35c/common.mk) specify the joy-test path. It needs Make, a shell/basic file utilities, a matching m68k-elf GCC/binutils toolchain including compiler, assembler, linker, `nm` and `objcopy`, compatible libgcc, SGDK headers and `libmd.a`, `md.ld`, boot `sega.s`/`rom_head.c`, and Java for `sizebnd.jar` padding/checksum generation. The README names provided Windows GCC 13.2 binaries and requires separate toolchain installation on other operating systems. LTO compatibility between GCC and `libmd.a` matters.

`rescomp.jar` is needed when rebuilding SDK resources or a sample that declares resources. The checked joy-test has no `.res` input of its own. A complete source rebuild of the SDK also needs its resource/compiler and sound/tool inputs, including Z80 assembly and resource compression tooling declared by the SDK; those are not supplied by merely copying `main.c`. The ready-ROM acquisition route avoids installing the toolchain at run time but does not remove its provenance audit. No specific third-party Docker image, Linux helper or SDK bootstrap was executed or qualified here.

Use `sample/joy-test/out/rom.bin` at v2.11, not a current-master path guessed from a newer SDK. `.bin` is an advertised Mega Drive format in the pinned catalog and supported by [Genesis Plus GX documentation](https://docs.libretro.com/library/genesis_plus_gx/). Launch through normal `megadrive` configgen with `libretro/genesisplusgx`. This is a cartridge, not Sega CD or 32X. With the optional system boot ROM disabled it needs no external firmware. Binary/source equivalence, complete resource provenance, a local digest and native input assertions remain open.

## Atari2600/Stella

### First choice: 8bitworkshop controls example

The inspected 8bitworkshop source pin is `66e137e19582f7619aa29ee222c2f4f3a7372a02`, returned by the [tree API](https://api.github.com/repos/8bitworkshop/8bitworkshop/git/trees/66e137e19582f7619aa29ee222c2f4f3a7372a02?recursive=1). The actual candidate is [presets/vcs/examples/controls.a](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/presets/vcs/examples/controls.a), not the web IDE or its emulator. This is a source-only lead. No separately published corresponding ROM was established in the inspected metadata, and no ROM hash exists from this research.

The source initializes X and Y to 80. Each frame `MoveJoystick` reads player 1's `SWCHA` direction bits and changes X/Y within fixed bounds. It draws an eight-row cat-head sprite from explicit bitmap and palette byte tables. No external image, font or sound file is included. It does not read the fire input `INPT4` and does not display named button states. The `SWCHB` Game Reset switch branches back to initialization.

**[INFERENCE]** With all directions released, the cat should remain at its current location. A held Right should move it right across successive rendered frames, release should stop it at the new location, and a later Left hold should reverse direction. A source-grounded automatic observation would locate the sprite and compare the direction of its motion before, during and after each held input. A no-input control must remain stationary, and the hold must end before reaching the position bound, where continued hold and release otherwise look identical. This demonstrates directional digital guest input, including release stopping movement. A single still cannot distinguish a held direction at a bound from release. It is not evidence for the fire button and does not display an instantaneous button bitmap.

This is still an improvement over color bars: input controls guest-rendered position. Whether directional motion is the preferred ordinary-input oracle, rather than a face-button indicator, remains a planning choice. It must not be advertised as full controller-button coverage.

The [8bitworkshop README license section](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/README.md#license) explicitly places included `presets/` code samples under CC0 unless an individual sample states otherwise. The [presets license](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/presets/LICENSE) contains CC0. `controls.a` has no conflicting notice. Its bitmap/color tables are part of that sample, rather than an untraced external artwork file. The IDE's GPLv3 license is not the sample license, and the sample grant does not relicense third-party assembler includes.

### Build dependencies and a real compatibility issue

The complete direct source input set is `controls.a`, `vcs.h`, `macro.h` and `xmacro.h`, plus DASM in raw-binary output mode. The program's `$f000` origin and `$fffc` vectors describe a conventional 4 KiB cartridge. A standalone assembly route needs no Node, npm, browser, IDE emulator, cc65, batari Basic or ROM-sourced BIOS. If DASM itself is built, it needs a C compiler, C development/runtime environment, Make and normal host utilities, per the [DASM README](https://github.com/dasm-assembler/dasm/blob/09270863f5f70e5200c30d2778f654ff7a40adba/README). A clean ROM build and output size have not been observed.

The exact include versions matter. The pinned workshop's [macro.h](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/src/worker/lib/vcs/macro.h) defines `TIMER_SETUP` and `TIMER_WAIT`. Its [xmacro.h](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/presets/vcs/xmacro.h) defines those same macro names, and `controls.a` includes both. **[INFERENCE]** That duplicate-definition combination is a build risk, not a proven working recipe. No build was run to decide DASM's behavior here.

A concrete conservative include alternative is DASM 2.20.14.1, revision `09270863f5f70e5200c30d2778f654ff7a40adba`, whose [standard macro.h](https://github.com/dasm-assembler/dasm/blob/09270863f5f70e5200c30d2778f654ff7a40adba/machines/atari2600/macro.h) is version 1.09 and does not define those timer macros. Pair that standard include set with the pinned sample and its `xmacro.h`, then qualify the assembly result. This is an explicitly identified dependency choice, not a statement that such a ROM already exists. The older macro's default `CLEAN_START` uses the undocumented `LXA` instruction; it offers the existing `NO_ILLEGAL_OPCODES` build option. A qualification record must state the chosen option and resulting artifact, not quietly change the source or pretend two builds are identical.

DASM's [legal notice](https://github.com/dasm-assembler/dasm/blob/09270863f5f70e5200c30d2778f654ff7a40adba/README) grants GPL-2.0-or-later, separately from CC0. The standard includes identify their upstream authors and do not carry a separate permissive grant in the inspected text. Macro expansion contributes startup/sync instructions to the ROM. Do not label the whole resulting ROM CC0 based only on the sample. Conservatively preserve the companion include sources/notices and assess GPL obligations for their included code before distributing the result. The fact that an assembler is GPL does not by itself make all assembly output GPL; the copied macro code is the issue here.

The catalog advertises `.a26` and `.bin`, and [Stella's documentation](https://docs.libretro.com/library/stella/) supports both. Use an ordinary raw cartridge file through stock `atari2600` configgen and `libretro/stella`, with the actual controller type and NTSC presentation recorded. Do not substitute Stella 2014, Stella 2023 or an IDE emulator. No external firmware is identified for this route. Stella documents RetroPad Start as the console Reset switch, so plain Start may recenter the sprite through the ROM's reset branch. That is a guest reset, not application exit. Guide+Start still needs separate native consumer-effect and frontend-return evidence.

### Alternatives, negative findings and proposal boundary

- The [missingno-vcs-tests project](https://github.com/ajoneil/missingno-vcs-tests) is a new first-party MIT hardware-test lead, with source-build instructions using DASM and ordinary Atari includes. Its [RIOT io-ports source](https://github.com/ajoneil/missingno-vcs-tests/blob/main/roms/riot/io-ports.asm), blob `29d022035cc166dad668984fa8e0f3f8bcb7af43`, configures all port-A pins as outputs, writes patterns and tests readback. Its header explicitly says nothing from the outside world is in that read path. A PASS screen from that test cannot prove gamepad input. This is a conclusive rejection of that particular test for guest-input evidence, not a claim that every file in the project lacks suitable behavior.
- The [8bitworkshop missiles example](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/presets/vcs/examples/missiles.a) moves objects and cycles colors from hardcoded data. It does not read joystick input. The [piatable example](https://github.com/8bitworkshop/8bitworkshop/blob/66e137e19582f7619aa29ee222c2f4f3a7372a02/presets/vcs/examples/piatable.a) also animates without input. Their names and animated output are not evidence of input sensitivity.
- `a26-kickstart` remains a small procedural rendering lead but lacks controller polling, as recorded in the existing catalog. It cannot establish the required input transition unchanged.
- Hardware joystick testers, commercial test-cartridge downloads and source dumps with no clear distribution grant are not replacements for a stock-launchable rights-supported ROM.

If the project requires a stable instantaneous fire-button/held-state panel rather than motion, or rejects the companion-include licensing/build complexity, a small project-owned Atari ROM with procedural indicators is a **PROPOSAL requiring scope acceptance**. The same fallback could remove the SNES font uncertainty if that becomes a rights blocker. No such fixture has been designed, created, accepted or proven necessary here. It would be a cartridge-content task, never a per-emulator input patch or overlay, and would still need full stock launch and native qualification.

## Cross-case evidence and Guide handling

These source leads can inform guest-input assertions; they cannot prove stock Guide effects. For each selected fixture, later qualification must separately establish:

1. An acquired or built cartridge, its measured SHA-256, exact source/tool/dependency inputs, notices, asset disposition and binary/source relationship. An upstream API digest or Git blob ID is not a measured local fixture digest.
2. Actual launch through unchanged stock configgen with the required core and suite-owned disposable controller mapping, backend/device discovery and a semantic guest-rendered neutral/press/hold/release/changed-input observation. Confirm no-input controls instead of assuming a moving or lit screen is input evidence.
3. Every applicable configured common and emulator-context shortcut, through native gamepad, the existing adapter, unchanged stock hotkeygen and an observed consumer effect. Inspect the pinned contexts to determine the complete action set. Do not narrow it to menu/exit or infer nonapplicability from a fixture's lack of an in-ROM menu.
4. For Guide+Start, actual emulator termination, launcher completion and EmulationStation readiness/return. Plain guest Start must remain distinguishable from that host chord, especially NES boot/help behavior and Atari Reset.
5. Real server PNGs at frontend-ready, fixture-rendered, guest-response and applicable shortcut checkpoints, with accessible failure captures. Retain them for optional review, while machine assertions decide acceptance without a mandatory manual gate.

No screenshot regions, tolerances, timing budgets, executable predicates or passing results are established by this source research. Emitted keys, event-receiver results, processes and PNG existence cannot replace those observations. Firmware requirements for other required systems remain explicit operator-supplied prerequisites outside code, images and fixture bundles.

## Decision impact and exact remaining question

The former SNES and Atari gaps are no longer just unanswered project-discovery questions. There are concrete upstream input-sensitive source options with inspectable render paths and rights evidence. The remaining work is qualification, plus the choice of Atari observation style.

The planning question is: **Should qualification proceed with unchanged PVSnesLib `controller.sfc` and 8bitworkshop `controls.a`, accepting single-button text transitions for SNES and direction-driven motion/stop/reverse for Atari, subject to their stated font, linked-component and include-rights/build checks; or should an explicitly accepted project-owned procedural cartridge replace either where those constraints are unsuitable?** The NES and Genesis recommendations remain their existing pinned leads, with binary/source and asset qualification still required. This report does not authorize a build, native experiment, fixture distribution or implementation, and it does not change the six-case regression gate.
