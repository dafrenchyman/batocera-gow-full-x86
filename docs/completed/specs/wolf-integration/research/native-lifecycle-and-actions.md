# Research: native Wolf lifecycle and stock Guide-action assertions

## Question

Can the accepted native regression suite use unmodified Wolf and Batocera while proving actual guest input and all applicable configured Guide shortcuts? Which lifecycle responses and visible states are insufficient evidence?

A source-supported route resolves the design question, not target compatibility or runtime qualification. A failure to find an assertion is an unresolved prerequisite, not permission to omit that action.

### Native API and state ownership

Primary Wolf sources:

- [API request/response declarations](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/api/api.hpp).
- [HTTP routes](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/api/unix_socket_server.cpp).
- [Endpoint implementations](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/api/endpoints.cpp).
- [Lobby setup and stop handlers](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/sessions/lobbies.cpp).
- [API reflection fields](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/events/reflectors.hpp).

Observed in source:

1. The existing API exposes `GET /api/v1/sessions`, `GET /api/v1/lobbies`, `POST /api/v1/lobbies/create` and `POST /api/v1/lobbies/stop`. Native lobby creation accepts an existing profile ID, name, optional PIN, video/audio settings, optional client settings, relative runner state folder and serialized runner. No persistent app/profile registration is needed by this route.
2. Wolf generates the lobby UUID server-side, stores the lobby before compositor readiness and waits up to 20 seconds in the create endpoint. On timeout it returns an error without the UUID; that endpoint shows no rollback. A client-side timeout can also lose a successful response. **Inference:** create failure does not establish absence; retrying can create a second lobby.
3. The setup callback starts the runner on a detached thread, then signals setup completion. A successful create response does not prove container creation, frontend readiness, non-root identity, native input discovery or probe readiness.
4. Lobby listing includes ID, name, initiating profile, PIN-required flag, serialized runner and connected session IDs. It does **not** expose the runner state folder. Recovering a lost create response needs a unique run marker plus expected profile/runner evidence and effective Docker inspection; a matching name alone is not ownership proof. Multiple or inconsistent matches remain ambiguous.
5. The stop endpoint checks lobby ID/PIN, fires a stop event and returns success. The lobby handler removes the lobby from the in-memory list; the Docker runner separately handles the stop event. Neither HTTP success nor absence from `/lobbies` proves container removal.
6. The create continuation retains the lobby independently of the list. **Inference:** a stop before runner startup is not source-level proof that a late continuation cannot still start it. An unresolved create/stop must remain incomplete cleanup; do not delete its home merely because no container exists at one instant. This source does not establish a finite cancellation barrier for every startup failure.
7. An absent PIN means an open lobby. Proposal: use an ephemeral suite-private PIN, retain it only as needed for owned stop requests, never log it, and still monitor for unexpected connected sessions. This reduces accidental joining; it is not atomic server reservation.
8. Session serialization includes AES key/IV and client metadata. Discovery should parse only needed identity/activity fields in memory and never retain raw session responses. Lobby runner serialization can contain environment/settings too; avoid raw API dumps.

### Native mounts, pulling and cleanup

Primary sources:

- [Native runner argument/mount construction](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/sessions/common.cpp).
- [Docker runner](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/moonlight-server/runners/docker.cpp).
- [Underlying Docker API client](https://github.com/games-on-whales/wolf/blob/ee271038da2b81c9e54c28c9daa7558692d415d6/src/core/src/platforms/all/docker/docker/docker.cpp).

The state folder is resolved through separate local and Docker-host roots. Native setup binds the resulting host path to `/home/retro`, its `udev` child to `/run/udev/`, the configured fake-udev helper, compositor/audio sockets and selected GPU resources. Preserve these native bindings rather than adding a competing home bind.

The container name is `<runner-name>_<lobby-UUID>`. Record the exact Docker ID and inspect image, run marker, expected mounts and identity before opening the input gate; a prefix is insufficient.

The underlying Docker `create` implementation automatically pulls on an image-not-found response. Therefore checking an immutable image reference string is not enough to honor the no-pull boundary: preflight must establish the exact image is already present. Concurrent external image removal remains a race; source inspection does not establish a stock per-request no-pull switch. Do not promise that preflight disables Wolf's internal fallback.

The Docker runner's explicit stop/remove-on-exit branch is conditional on `WOLF_STOP_CONTAINER_ON_EXIT=TRUE`; other effective Docker options may also affect removal. The suite must inspect reality and remove only its exact recorded stopped container when needed, without changing Wolf's environment. Never assume lobby stop removes it.

The underlying client does not set a curl deadline in the inspected request helper. Coordinator deadlines bound its own calls/waits, not cancellation of already dispatched Wolf operations. Lost access or unresolved late startup is a nonpassing result with retained known resource identities, not a successful timeout cleanup.

Primary Xlib sources explain why a handler installed only around a later `XSync` would be too late. [`XGetWindowProperty`](https://github.com/mirror/libX11/blob/master/src/GetProp.c) waits in `_XReply`, invokes error dispatch before returning and returns non-success after an error. [`XErrorEvent` and `XErrorHandler`](https://github.com/mirror/libX11/blob/master/include/X11/Xlib.h) use native unsigned-long resource/serial fields and an int-returning Display/event-pointer callback. [`XSetErrorHandler`](https://github.com/mirror/libX11/blob/master/src/ErrHndlr.c) is process-global and returns the real default-handler address when none was installed. [`_XError`](https://github.com/mirror/libX11/blob/master/src/XlibInt.c) dispatches through that global function pointer. These sources informed the ABI and scope; they are not packaged-runtime measurements.

The bounded source repair serializes module-owned property scopes, locks the display, drains prior errors under the original policy and captures the exact next request serial. Only BadWindow for that GetProperty request's display, resource, serial and opcode/minor is recoverable. Every other error delegates to the previous handler; its pointer is restored in `finally` before the display unlocks. The callback stays module-owned for process lifetime, with live per-request state and a setup barrier for foreign dispatch before the previous pointer has returned. This avoids a freed ctypes trampoline after restoration. Independent concurrent changes to Xlib's process-global handler are outside this observer's contract. Missing/malformed properties remain unavailable, including trailing bytes after a one-item prefix. Native `:0`, non-root and authentication restrictions are unchanged. There is no supervision, stock/input, deadline, exit-classification or return-readiness change.

## Findings

The pinned sources support native ephemeral lobbies and stock gamepad-to-hotkeygen-to-consumer tests without rewriting upstream components. Actual installed capability and safe startup-failure recovery remain unqualified.

The major fixture gap is not simply finding bootable homebrew: a useful regression fixture needs input-sensitive **and** state/time-sensitive observations, with an additional disc scenario where applicable. Qualification may require several fixtures/scenarios under one required backend/core case. Do not force one static ROM to prove everything or relax all-applicable-shortcut acceptance.

No upstream code change is justified by source-level anomalies alone. If native qualification confirms a stock action cannot satisfy the accepted behavior, bring that blocker back to planning rather than patching Batocera or redefining success.

## Dead Ends / Failures

- The first configgen directory lookup omitted its nested `configgen` package and returned 404. Parent/tree discovery resolved the actual paths; this was not absence of the generators.
- Creating a direct Docker container, invoking `hotkeygen --send`, injecting the emulator's final keyboard shortcut, or using the receiver alone bypasses required native/gamepad behavior and is not an acceptance substitute.
- A create/stop HTTP success, a lobby-list absence or one empty container scan does not prove the complete lifecycle/cleanup contract.
- Automatically pulling an absent image or retrying ambiguous startup violates the accepted suite boundary. Exact local image preflight is necessary but does not cancel stock fallback behavior after a race.
- Generic pixel changes, static boot screens and emitted-key logs cannot qualify save/load/rewind/time/disc behavior.

## Decision Impact

Keep the native API approach, shared-root homes, automatic semantic checks, retained screenshots and six required cases. Preserve explicit incomplete cleanup for ambiguous/late startup. Add target qualification checks for local image availability, effective container removal policy, safe API parsing and exact ownership recovery; none permits Wolf configuration changes.

Fixture selection must account for state/history/time and applicable disc effects, not just a live button display. Detailed fixture rights/build leads belong in the sibling research reports. A project-owned procedural fixture is an option only if accepted, not an implementation authorized by this report.
