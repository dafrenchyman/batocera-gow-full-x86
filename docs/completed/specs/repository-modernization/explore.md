## Decisions

### One package and one complete cutover

Use the accepted concrete package `src/batocera_gow/{host,builder,runtime}` in one installed Python project. Put non-Python build/runtime inputs under `build-assets/` and tests under root `tests/unit/` and `tests/integration/`, retaining execution-environment boundaries within those groups. Keep one project metadata/lock owner, not separately versioned distributions or a second independently maintained flat runtime.

Host entry points import the installed package. Builder execution uses its provisioned project interpreter and explicitly available installed source. Runtime deployment stages only the required package subset and owned assets beneath the existing `/opt/gow-full-x86` boundary. Its launch commands and subprocesses must resolve that package without a development checkout, host venv or global `PYTHONPATH`. Existing operational `/opt` entry-point paths may remain thin launchers for the one maintained implementation, not duplicate implementation or old source-layout import shims. No first-party source remains executable only through `experiments/gow-full-x86`.

Relocate host tools, builder modules, all runtime modules/probes, all remotely executed source and the new integration coordinator. Update bare imports, `__file__` ancestry assumptions, shell commands, installed module entry points, `/scripts` binds, builder build contexts, Nix paths, resource lookup, runtime sibling calls, test fixtures and documentation together. Remove obsolete requirements/bootstrap/import compatibility paths. Never reformat extracted upstream trees.

Keep source/caller migration, checked remote extraction and behavior-preserving maintainability cleanup in one coordinated cutover ticket, with one integration owner for shared contracts and conflicting edits. Do not split host, builder and runtime moves into independently completed tickets that require compatibility code or leave a broken intermediate application. Independent application-coverage and hook/secret-gate tickets follow the installed cutover; whole-outcome verification depends on both. The cutover remains blocked on the sibling's passing old-layout native baseline.

### Build and runtime assets

Keep Python modules under src/batocera_gow/. Use the already selected build-assets/ directory for non-Python image inputs: build-assets/release.json for the pinned release declaration, build-assets/builder.Dockerfile and build-assets/bridge.nix for build definitions, and build-assets/runtime/alsa.conf for the project-owned audio configuration. They do not need to become Python package data or live beside Python modules merely because their consumers move.

Configure asset paths from the project/build-input root rather than assuming they are siblings of a Python file. Preserve existing in-image runtime destinations when staging the required assets; do not copy the entire development environment or build-assets tree into Batocera. Include consumed assets in source/cache fingerprints. These are concrete placements within the accepted layout, not changes to stock Batocera configuration.

### Manual generated-artifact cleanup

The user explicitly selected **Keep cleanup manual** after reviewing the proposed post-verification retention amendment. Do not add automatic image/output deletion, failure-payload cleanup, a retention scheduler or implicit remote cleanup to normal builds. The original Ready implementation contract and four-ticket grouping remain unchanged.

Manual permission covers old local project images and obsolete generated data under `output/`, plus old tested images on the existing Wolf server. Server cleanup must protect every image referenced anywhere in the active `config.toml`, resolving aliases/digests to immutable identities, whether or not the corresponding app is running. Protect all containers, current build inputs, the last verified candidate, private/native evidence, provenance/manifests, shared verified downloads, original Batocera state, libraries and unrelated resources. Require positive ownership/identity and fresh non-use/reference checks; never force or globally prune. Retired payloads are no longer cache inputs or reusable evidence, while their retained records remain historical provenance.

### Portable roots and owned destinations

Remove the fixed `PROJECT` path and `OLD_SOURCE` exclusion logic from maintained code. `OLD_SOURCE` only names an unrelated checkout to avoid; it supplies no build input. Do not retain that obsolete concept as an environment variable, configured exclusion or required checkout. The original Batocera checkout remains protected from mutation without needing to exist or have a known location.

Resolve or explicitly configure project/build-input roots and owned destinations at entry points. Replace the personal `/home/operator/...` deployment-root default with explicit remote destination configuration and inject it into the checked remote implementation. Local-only commands require neither personal deployment paths nor SSH settings. Preserve resolved-path containment, symlink-escape refusal, applicable independent Git metadata/source-provenance checks and on-host ownership/canonicalization immediately before remote writes.

Verify installed tools from a differently located independent checkout with no original Batocera checkout available, using declared assets and inputs. Exercise allowed destinations and rejection of out-of-root, ancestor and symlink-escaped destinations, plus configured remote ownership boundaries. This changes source/tool portability, not deployed app/runner/home identities or persistent userdata; existing experimental and original Batocera state remain protected.

### Interpreters, dependencies and ownership

Batocera determines the Python major/minor. The retained stock inventory is CPython 3.12 and pinned Buildroot source declares 3.12.8. Confirm the full version in the actual selected image during authorized implementation before finalizing `.python-version` and builder interpreter provisioning. The builder's observed Debian 3.13.5 is not the project interpreter.

Permit host Python 3.12.x, including the user's reported installed NixOS 3.12.12, without rechecking that observation. On NixOS explicitly select Nix Python through `UV_PYTHON` and set `UV_PYTHON_DOWNLOADS=never`. uv owns project environments and `uv.lock`; a shell can supply binaries/settings without managing the OS or replacing dependency ownership. Provision the stock-full-version builder interpreter and locked dependencies before networkless assembly. Availability of a suitable interpreter artifact and its actual imports are qualification prerequisites, not facts established here.

Keep OS Python and Batocera Python unchanged. Do not copy a host virtualenv/native extensions or include uv, development tools or the builder environment in the final runtime. Host tomlkit and optional dependency-injector must not leak into runtime or the stdlib remote payload. Existing stock Pillow, evdev, pyudev and stock hotkeygen/configgen dependencies remain valid.

The Python policy is settled. The builder is the temporary Docker container that runs image-assembly scripts, not the user's computer or Batocera itself. Its current Dockerfile invokes Debian's python3; retained package metadata reports 3.13.5. Applying the selected Batocera-led version there is implementation work. Recording the stock patch version during that work is a build check, not another Python choice for the user or a reason to recheck their reported host version.

The package/import/resource checks mean checking that moving files does not break Python imports or lookups of assets such as release.json and alsa.conf, and that host development libraries are not copied into Batocera. The src layout and dependency boundaries are already selected. These are checks of the resulting implementation, not unresolved architecture questions.

Every stateful service receives configured collaborators and the settings it needs through explicit constructor parameters. Resolve environment/files and assemble production dependencies at entry points. Preserve the accepted form `ReportService(client: ApiClient, config: ReportConfig)`, not `client or ProductionClient()`, a service locator or a container in business methods. Pure helpers need no container or invented protocol. Injected resources are borrowed unless ownership is explicitly transferred; their owner must clean up deterministically after success, failure and partial startup. dependency-injector is allowed outside Batocera only, not required for every helper and never directly or transitively imported/staged into the image.

### Maintained ephemeral remote source

Replace long `REMOTE_HELPER`, `inspect.getsource` assembly and the ad hoc diagnostic-writer program with ordinary checked Python modules. Keep the shared activation transaction in one stdlib-compatible source implementation used by both host tests and remote payload, separate from host tomlkit parsing. Package only the remote-required stdlib modules into a self-contained ephemeral SSH payload for each invocation. Do not install a remote helper/service persistently.

Retain JSON requests/responses, recognized operations, remote canonicalization immediately before writes, ownership and image/state gates, compare-before-write activation, sanitization and nonsecret failure translation. Private configuration requests stay in transport/process memory rather than saved payloads, debug logs or diagnostic artifacts. Existing intentional Wolf configuration/owned diagnostic writes remain governed by their current contracts. Source packaging must not become a mechanism for assembling unchecked Python strings or accepting arbitrary operator shell commands.

### SSH configuration and local environment files

Require `BATOCERA_GOW_SSH_TARGET` only for remote operations. Accept direct `user@IP-address`, `user@hostname` or a normal OpenSSH host alias. Default authentication to normal local OpenSSH configuration/agent; allow `BATOCERA_GOW_SSH_IDENTITY_FILE` as an optional path override. Never use personal source defaults or private key contents. Validate destination/options as data, retain argument-vector execution, `BatchMode=yes` and `StrictHostKeyChecking=yes`, and inject the configured transport. Local build, tests, package operations and dry-run/local-only paths do not need SSH settings.

Preserve actual `.env` values and restricted mode, the ignored `.env` boundary and neutral `example.env`. Update the example's temporary unsupported-code note only when the application supports the interface. Manual shell exports remain supported. The approved modernization additionally permits explicitly selected dotenv files, without automatic discovery or parent-directory searching. Never read or copy private keys into requests, images or evidence.

Use host-only [python-dotenv](https://bbc2.github.io/python-dotenv/#load-configuration-without-altering-the-environment) with `dotenv_values` and a focused host settings module. The user approved explicit file selection and frozen typed configuration loaded once per command invocation or authorized native pytest session. Existing `SSHConfig`, `NativeConfig` and content-root configuration provide validation seams to reuse, not a reason to create competing copies of domain rules.

Explicit command overrides take priority over exported environment, which takes priority over the selected dotenv file, then safe defaults. Without a selected file, use explicit values/environment/defaults without dotenv discovery. Preserve `os.environ`; do not call import-time `load_dotenv`, instantiate global settings or cache one process-wide ambient configuration. Entry points and authorized session fixtures assemble the required configuration and inject only each consumer's settings. Local-only commands do not validate or require remote settings, and imports/collection/default tests do not load native configuration. Missing explicitly requested files and invalid required values produce nonsecret errors rather than silently selecting another target. Settings do not grant native/resource authorization. Keep the parser out of Batocera and the stdlib-only remote payload.

[Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/) was considered but not selected. Its dotenv parsing and richer validation/model layer add dependencies without replacing existing domain checks. The lightweight parser plus typed configuration fits the existing code. A `settings.py` or `config.py` module organizes source resolution and assembly; it does not justify import-time environment access. Record library pins and implemented option names during the authorized cutover rather than claim this loader exists now.

Refactor demonstrated problems while preserving behavior and execution-environment boundaries. Keep each fact or rule with its owning code. Do not impose arbitrary file-size limits, split every large module or introduce abstractions solely to satisfy tooling.

Acceptance includes a factual design review of module responsibilities, shared rules, state and dependency ownership, justified abstractions, and removed dead code. Tool success or coverage alone cannot discharge this review. Keep planning headings sentence case under the shared writing standard.

Permit only diagnostic-specific justified import exceptions where real typing support is unavailable, not blanket ignores or exclusions for difficult runtime code. Preserve specific caller-actionable failure semantics.

Use pytest with the root unit/integration organization described below. Migrate substantive behavioral regressions. Delete tests that pin wording, implementation spelling, incidental structure or source text rather than repinning them to new paths. Assertions about contractual bytes, argv, metadata, stock preservation and privacy remain substantive. Remove `sys.path` and ad hoc file-import loaders used only to evade package installation. Keep legitimate subprocess fixtures and environment-specific imports.

Measure at least 80% application line coverage over all real host, builder, runtime and remote modules, including unexecuted source and the new coordinator. Report branches without a separate branch percentage floor. Use the independent line checker after a fresh report, not combined fail-under percentages, stale reports, helper-only coverage or a no-source success. Environment runs may contribute translated/combined data when necessary; report exactly which runs contributed and retain uncovered lines for unexecuted environments. Adopt the applicable template hooks for Python, documentation/config formatting and Nix. Preserve Alejandra as formatter and Statix/deadnix as check-only. No frontend application, React/ESLint/Vitest hooks, host-management scaffolding or mandatory root flake is needed. Keep the pinned runtime Nix closure separate from optional development tooling. Use the ordinary Yelp system-language hook with `args: ["--baseline", ".secrets.baseline"]`. Resolve the latest published stable release during implementation and align its pinned hook revision and managed executable. The saved primary-source check identifies v1.5.0 on 2026-10-28, not a tested installed tool. Add no `--no-verify`, custom scanner, history scan or new CI scope. Review baseline candidates privately; do not accept real credentials to make checks pass. Remediate/remove genuine secrets and arrange credential rotation when needed. Retain the user's ordinary stable-release Yelp revision in the hook example. Apply the template's reviewed immutable-revision convention to other applicable hooks without confusing a release tag with an immutable commit or using a floating latest/unreleased branch. Keep the selected Yelp version and installed executable aligned.
