## Problem statement

The application works, but its maintained source is still a flat collection under `experiments/gow-full-x86/`. Host orchestration, disposable builder programs, stock-image runtime, SSH-executed programs and tests depend on bare imports, directory ancestry and adjacent assets. Moving the directory alone would break those relationships. Broad typing or docstring changes can also break the source extracted into remote programs.

The repository has established standards but no demonstrated complete project packaging, locked development environment, whole-source compliance, application coverage or reviewed secret gate. Copying ProjectTemplate unchanged would make matters worse. Its package is tooling-only, its frontend hooks do not apply, and its coverage utility permits a no-application result that is wrong for this repository. Existing host tools also commit a personal SSH destination and key path.

The user needs one installed project that keeps execution-environment boundaries explicit, checks all maintained source and preserves the working Batocera/Wolf behavior. Cleanup must not change deployed names, state or upstream software. It must be protected by a maintained native baseline established before the broad production migration, not by rebuilding the test workflow at the same time as its subject.

The operator also needs one repeatable way to qualify a generated image. Preservation, packaged smoke checks, local tests and native scenarios exist separately, but no installed command combines their actual results into one image-bound qualification. Private one-off verification scripts are not that maintained command.

## Solution

Deliver one installed Python project under `src/batocera_gow/`, with `host`, `builder` and `runtime` subpackages, non-Python inputs in `build-assets/`, and root `tests/unit/` and `tests/integration/` organized further by execution prerequisites. Migrate every caller, wrapper, asset lookup and provenance input. Remove the obsolete source layout rather than retain forwarding modules or import aliases there.

The normal developer flow becomes root-level uv dependency synchronization, installed-package commands, pytest behavioral tests and a separate fresh-report application line-coverage gate. Applicable Ruff, mypy, documentation/configuration and Nix hooks check source without starting builds, native tests or remote operations. A reviewed Yelp detect-secrets baseline provides the selected ordinary commit-time secret gate.

Add the external installed `batocera-gow-qualify` command. It validates the selected immutable image and current build inputs, runs local tests and the independent fresh coverage gate, exercises packaged smoke checks against the exact image, then runs the complete explicitly authorized Wolf matrix. It writes one qualification report. Keep pytest and development dependencies outside the runtime image; building remains a separate explicit action.

Remote operators supply `BATOCERA_GOW_SSH_TARGET` through exported environment or an explicitly selected `.env` file; an optional `BATOCERA_GOW_SSH_IDENTITY_FILE` supplies a path override. A host settings module uses python-dotenv and existing typed validation to resolve configuration once per invocation or authorized native pytest session. Entry points inject configured dependencies into services. Local-only commands need no SSH settings. Normal OpenSSH config/agent authentication remains valid, without personal fallbacks or implicit dotenv discovery.

For each SSH invocation, the host packages maintained, checked stdlib remote source into a self-contained ephemeral payload. The server receives a JSON request and returns a JSON response under the existing ownership, activation and privacy contracts. No persistent helper installation is needed. The same activation implementation remains shared with host behavior tests.

Delivery has a strict dependency boundary:

1. [Wolf integration](../../../completed/specs/wolf-integration/spec.md) first establishes and passes the maintained required native gate against the existing operational layout. Necessary coordinator, diagnostic/fixture additions and test-owned state are allowed there; broad production source migration is not its prerequisite.
2. This work relocates all application source, including that coordinator, and adopts the declared standards across it. Independent secret-gate preparation does not waive the native prerequisite for broad production moves/refactoring.
3. The migrated package passes the local/static/coverage and real preservation/import gates, then the same required native gate. Source-sensitive README/current documentation records the actual exercised commands, environments and limits. A moved tree alone is not completion.

Planning defines this specification and its exploration. Ready approval does not authorize implementation, installations, source moves, hooks, scans, builds, SSH, deployment, publication, Git changes or native execution.

## User stories

1. As a contributor, I want installed imports, locked dependencies and predictable root commands so I can work from a clean clone without `sys.path` manipulation or hidden asset assumptions.
2. As a maintainer, I want meaningful typing, docstrings, formatting and behavioral tests across host, builder, runtime and remote source so difficult environments cannot disappear from compliance or coverage.
3. As an operator, I want my SSH destination and optional key path supplied outside shared source so other users do not inherit my personal configuration and local-only work needs no server credentials.
4. As an operator, I want maintained remote code delivered ephemerally so its checked behavior and ownership/privacy protections do not depend on long strings or server installation.
5. As the owner of a working deployment, I want the native suite to pass before and after the broad migration so source cleanup does not silently alter stock metadata, launch/input behavior, app identity, persistent state or unrelated services.
6. As a contributor, I want applicable lightweight hooks and reviewed secret prevention so routine commits catch useful mistakes without launching heavy tests or quietly approving actual credentials.
7. As a contributor, I want individually selectable real-Wolf pytest cases with shared image preparation and isolated case state, and a mandatory check that my explicitly built image matches current inputs, so a stale image cannot falsely validate my changes.
8. As an operator, I want one external command to qualify the exact image I built, with one truthful report, so I do not manually assemble separate host, packaged-runtime and Wolf invocations or mistake a smoke pass for full qualification.

### Configured dependency injection and resource lifetime

Entry points choose configuration sources, validate boundary data and assemble collaborators. Services receive already configured dependencies and only the settings they need. Preserve the accepted constructor pattern:

```python
class ReportService:
    def __init__(self, client: ApiClient, config: ReportConfig) -> None:
        self._client = client
        self._config = config
```

This illustrates dependency ownership, not a new report feature. Apply it to paths, command/transport clients, configuration, clocks/ID sources where they affect decisions and runtime resource collaborators. Do not hide production construction behind `dependency or default`, read ambient environment deep inside services, use service locators or inject an application-wide container into business logic. Use concrete types unless a narrower consumer contract or alternate implementation justifies a protocol. Pure stateless helpers need no container machinery.

Injected resources are borrowed unless the interface explicitly transfers ownership. The owner uses context managers or explicit `try/finally` lifecycle, including partial startup failure, to close files, sockets, displays, descriptors, subprocess pipes and owned processes. Refactoring must not close a borrowed collaborator, signal foreign processes, reset unrelated input holds or delete replacement inodes.

dependency-injector is permitted for appropriate assembly outside Batocera. It is not required for every helper, must not leak directly or transitively into runtime imports, and must not be staged in the final image. The stdlib-only remote helper has its own stricter dependency boundary. Existing stock runtime third-party libraries are not prohibited by the library exception.

Keep the parser, private dotenv files and key material out of builder/runtime staging and the stdlib remote payload. Update neutral examples and exercised command/testing documentation during implementation with explicit file selection, source precedence and exported-environment usage. ### Opt-in native pytest preparation and freshness

Expose frontend, receiver and emulator scenarios as individually selectable pytest integration cases under `tests/integration/wolf/`. Reuse the maintained coordinator, probes, assertions, evidence and cleanup through checked application APIs. `conftest.py` contains thin fixture/configuration adapters, not a second lifecycle implementation or tests that only assert a CLI exit code. Root `uv run pytest` runs local-safe tests without builds, image upload, remote credentials or Wolf contact. Builder, packaged-runtime and native prerequisites remain separately selected. Collection is side-effect free, including explicit collection of the Wolf subtree.

Require deliberate native opt-in and explicit target/resource authorization in addition to selecting the test path. Resolve shared target, image/build-manifest, media-root and capability settings once through the host settings boundary rather than repeating a long CLI invocation for each case. Support explicit dotenv selection or exported environment with neutral examples, without letting file contents authorize execution. Load native configuration only in authorized execution fixtures, not during imports/collection. Document the exercised native command after implementation; naming its pytest switch is an implementation choice, not a working interface claimed by this spec.

Builds remain a separate explicit step.
